# Nested Azure File Sync Throttle Lab

This fresh lab targets subscription `95642268-5116-484d-9b88-7dfce8c20ce4`, tenant `0e478cd4-3e52-496d-ac3a-419ca58ba7ac`, existing resource group `rg-infra-winmig-apac-v-chengzhiz-poc`, and West US 2. Its `IAM-ReadOnly-Lock` has been removed; a `CanNotDelete` lock remains on a migration storage account. Do not remove that lock or delete the group as part of this lab. The design uses Azure File Sync and Azure Files public endpoints, plus a Hyper-V NAT network for the nested Windows Server guest. It creates no private endpoints, private DNS zones, service endpoints, VPN, or ExpressRoute resources.

Microsoft documents that Azure File Sync uses outbound HTTPS for FileREST and sync traffic. The nested guest uses host NAT because MAC spoofing isn't available for a public-cloud Azure VM network. See [Azure File Sync networking](https://learn.microsoft.com/azure/storage/file-sync/file-sync-networking-overview) and [nested Hyper-V networking](https://learn.microsoft.com/windows-server/virtualization/hyper-v/enable-nested-virtualization#networking-options).

## Deployment Gate

The deployment script checks the target group for a `ReadOnly` lock before running Bicep what-if or creating resources. The cloud-only deployment has succeeded, creating the storage account, SMB share, Storage Sync service, sync group, and managed-identity role assignments. The host remains gated on cloud endpoint success. If the endpoint is `Failed`, `Canceled`, or doesn't reach `Succeeded`, the script preserves workflow evidence and stops before creating the Hyper-V host.

## Run

From an Azure CLI session authenticated to the Contoso tenant and requested subscription, with Bicep installed:

```powershell
az login --tenant 0e478cd4-3e52-496d-ac3a-419ca58ba7ac
az account set --subscription 95642268-5116-484d-9b88-7dfce8c20ce4
.\scripts\Deploy-NestedAfsLab.ps1
```

The host administrator password is generated by the deployment script and stored locally as a DPAPI-protected value for the current Windows user. To display it only in your local terminal when you need to connect, run:

```powershell
$encrypted = Get-Content -Raw (Join-Path $env:LOCALAPPDATA 'AzureFileSyncNestedLab\host-password.dpapi.txt')
$secure = ConvertTo-SecureString $encrypted
$pointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
try { [Runtime.InteropServices.Marshal]::PtrToStringBSTR($pointer) } finally { [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($pointer) }
```

Do not paste that password into chat or logs. RDP is allowed only from the public IPv4 address detected by the deployment script. If your public address changes, rerun only after reviewing the deployment what-if and update the `/32` rule.

## Finish the Nested Guest

1. Start the deallocated host VM in Azure and connect by RDP from the allowed address.
2. Open Hyper-V Manager and connect to `NestedAfsServer`. Complete Windows Server 2025 Evaluation setup from the attached ISO. Create a local `Administrator` password for the guest.
3. Copy the `new/scripts` folder to the host (for example, through RDP drive redirection), open an elevated PowerShell session on the host, and run `Configure-NestedGuest.ps1`. Enter the guest Administrator password only in that host PowerShell prompt. The script configures guest NAT, initializes the guest data disk as `F:`, installs the Azure File Sync agent, and copies the experiment script to the guest.
4. In the nested guest console, run `C:\Program Files\Azure\StorageSyncAgent\ServerRegistration.exe` and complete the interactive Azure sign-in. Create a server endpoint for `F:\filestosync` in the Azure portal. Wait for the cloud and server endpoints to reach `Succeeded`.
5. In an elevated PowerShell window on the nested guest, run `C:\Users\Public\Documents\Run-NestedAfsThrottleExperiment.ps1`. The experiment runs baseline, 500 Kbps throttled, and recovery phases. It writes CSV results and telemetry samples under `C:\ProgramData\AzureFileSyncOps` and fails if the throttled phase records no uploads.

The first server registration and endpoint creation are intentionally interactive. This is required because the signed-in account is a B2B guest, which cannot use Entra VM sign-in for Windows VM access. Azure Owner permissions do not prove that the separate Storage Sync backend authorization failure is fixed.
